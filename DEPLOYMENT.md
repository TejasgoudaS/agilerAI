# Deployment Runbook — Render (backend) + Vercel (frontend)

Covers the two real gaps Render's free tier has for this app, and what we did to close them:

1. **No persistent disk on free web services** → local SQLite would reset on every sleep/wake cycle, not just redeploys. Fixed by using a free **Neon Postgres** database instead (Part B0) — `database.py` already supports this via `DATABASE_URL`, zero code changes needed.
2. **Sleeps after 15 min idle, 30-50s cold start** → four mitigations, already built into the code this session:
   - **Pre-warm ping** (`App.jsx`) fires `/api/health` the instant the page loads, so the wake-up overlaps with the user reading the page / uploading a PRD instead of only starting when they click Generate.
   - **Honest "waking up" UI** (`usePRDProcessor.js` + `aiClient.js`) — the availability check now waits up to 60s (was 2s, which would've silently misfired into a broken fallback path) and shows *"Waking up the AI engine — free-tier hosting sleeps when idle, this can take up to a minute..."* instead of looking hung.
   - **In-app "Keep Awake" toggle** — a button in the header (only visible when logged in) that pings `/api/health` every 4 minutes while enabled. **Off by default**, persists across reloads via `localStorage`. This is the one to flip on right before an interview/demo and off afterward, so you're not burning free instance-hours the rest of the time.
   - **External keep-alive ping** (Part D below) — a free uptime monitor as a backup/alternative to the in-app toggle, for whenever you can't rely on remembering to click it (e.g. an async take-home review).

## Part B0 — Create the free Postgres database (Neon)

1. In your new Neon project, go to the **Dashboard** → copy the **connection string** shown (looks like `postgresql://user:pass@ep-xxx.neon.tech/dbname?sslmode=require`).
2. Rewrite it for SQLAlchemy's driver naming — insert `+psycopg2` after `postgresql`:
   ```
   postgresql+psycopg2://user:pass@ep-xxx.neon.tech/dbname?sslmode=require
   ```
   That's your `DATABASE_URL`. Keep it handy for Part B2.

## Part B — Deploy the backend to Render

### B1. Create the service
1. Render dashboard → **New → Blueprint**.
2. Since there's no GitHub repo yet, the simplest path is: **New → Web Service → Deploy an existing image / Public Git Repository** isn't available without git — so first push this project to a GitHub repo (Render's Blueprint/web-service flow needs a git source; unlike Vercel/Railway, Render doesn't have a "deploy from local directory" CLI path):
   ```bash
   git init
   git add .
   git commit -m "Initial commit"
   # create a new repo on github.com, then:
   git remote add origin https://github.com/YOUR_USERNAME/agiler-ai.git
   git branch -M main
   git push -u origin main
   ```
   (`.env` is already git-ignored — verify with `git status` that it does **not** appear before pushing.)
3. Back in Render: **New → Blueprint** → connect your GitHub account → select the repo. Render reads `render.yaml` automatically and proposes the `agiler-ai` web service.

### B2. Set environment variables
When Render applies the blueprint, it'll prompt for the `sync: false` variables:
- `VITE_OPENAI_API_KEY` → your real OpenAI key
- `DATABASE_URL` → the Neon connection string from B0

`JWT_SECRET_KEY` is auto-generated by Render (`generateValue: true` in `render.yaml`) — nothing to do there.

### B3. Deploy
Click **Apply** — Render builds `server/Dockerfile` and deploys. First build takes a few minutes (installing crewai's dependency tree); watch the build logs in the dashboard.

Once live, verify: `curl https://your-service.onrender.com/api/health` should return the agent-list JSON. Note this **first request after any idle period is the slow one** (30-50s) — that's expected, it's exactly what Parts C/D address.

## Part C — Deploy the frontend to Vercel

1. Open `vercel.json` and replace `YOUR-SERVICE.onrender.com` in **both** rewrite destinations with your real Render URL from B3.
2. From the project root:
   ```bash
   vercel --prod
   ```
   Accept the auto-detected Vite build settings. **Do not** set `VITE_OPENAI_API_KEY` / `VITE_JIRA_EMAIL` / `VITE_JIRA_API_TOKEN` as Vercel project env vars (see the warning in `.env.example`).
3. Open the Vercel URL, register an account, and run a full generation to confirm the SSE stream works end-to-end through Vercel's rewrite → Render → Neon.

## Part D — Keep it awake (optional backup to the in-app toggle)

**For interview/demo day, the in-app "Keep Awake" button in the header is the primary tool** — log in, click it a few minutes before you need the app, click it off again when done. It persists across reloads, so if you flip it on the night before, it's still on the next morning.

Use an external monitor instead/as well when you can't rely on remembering to click it (e.g. someone else is reviewing the app async, or you want it awake for a whole take-home review window):

Render's math checks out either way: the free tier gives 750 instance-hours/month, and one service running continuously for a full month is ~720-744 hours — so keeping it awake around the clock still fits inside the free allowance; it's not abuse of the plan, it's just using the free hours you already have, continuously instead of intermittently.

1. [uptimerobot.com](https://uptimerobot.com) → **Add New Monitor**.
2. Type: **HTTP(s)**, URL: `https://your-service.onrender.com/api/health`, interval: **5 minutes** (well under the 15-minute idle threshold).
3. Save. That's it — Render will now see a request at least every 5 minutes and never spin down.

(Alternative if you'd rather not create another account: a scheduled **GitHub Actions** workflow in your new repo, `curl`-ing the health endpoint on a cron schedule, does the same thing using your existing GitHub login.)

## After it's live — housekeeping

- **Rotate your OpenAI key and Jira API token** — both were typed into this session's local `.env` in plaintext during development; issue fresh ones and set a spend cap on the OpenAI key from the OpenAI dashboard.
- **The `.cache/` (RAG embeddings) and `models/` (trained calibrator) directories are intentionally NOT persisted** on Render — no free disk to put them on. They're self-healing: the embedding cache silently rebuilds itself (a few OpenAI calls) on first search after a restart, and the calibrator just reports "untrained" until you click **Train from Jira History** again. Only the database (now on Neon) needed real persistence, and that's covered.
- To redeploy after a code change: `git push` — Render auto-deploys on push once connected to the repo.
